# 常见坑

## 坑 1：需求太模糊

**❌ 坏例子：**
```
帮我做个网站
```

**结果：** AI 自己猜技术栈、猜功能，交付的东西可能完全不是你要的。

**✅ 好例子：**
```
帮我做个网站：个人博客。
Next.js + Markdown 文件作为内容源。
支持标签分类、代码高亮、暗色主题。
部署到 Vercel。
```

---

## 坑 2：一次要求太多

**❌ 坏例子：**
```
做一个完整的电商系统：商品管理、订单、支付、物流、
客服、数据分析、推荐算法、多语言、多币种...
```

**结果：** 交付质量下降，每个模块都做得很浅。

**✅ 好例子：**
```
先做 MVP：商品列表 + 购物车 + 下单。
支付和物流后续迭代。
```

---

## 坑 3：不指定技术栈，交付后不满意

**问题：** AI 默认选了 Python，但你要 Node.js。

**解法：** 需求里明确写：
```
用 Node.js + Express + PostgreSQL，不要用 Python。
```

---

## 坑 4：交付后才发现缺功能

**原因：** 需求描述漏了关键功能。

**解法：** 用「验收」反推需求——先想清楚"怎么算做完了"，再写需求：

```
需求：任务管理工具
验收标准：
- [ ] 能创建任务（标题、截止日期、优先级）
- [ ] 能拖拽排序
- [ ] 能按标签筛选
- [ ] 数据持久化（刷新不丢）
```

---

## 坑 5：以为 AI 交付的代码不用看

**真相：** AI 交付的代码质量通常不错，但：

| 风险 | 应对 |
|------|------|
| 安全漏洞（SQL 注入、XSS） | 交付后跑一遍安全扫描 |
| 业务逻辑理解偏差 | 核心流程手动测一遍 |
| 依赖过时或有 CVE | `npm audit` / `pip-audit` |
| 密钥硬编码 | 搜索 `sk-`、`password=`、`api_key` |

---

## 坑 6：环境不一致

**问题：** 本地能跑，服务器跑不起来。

**解法：** 一律用 Docker。交付时确认有：
- `Dockerfile`（多阶段构建）
- `docker-compose.yml`
- `.dockerignore`
- `.env.example`（不含真实密钥）

---

## 总结：需求写好的四个要素

```
1. 是什么       —— 一句话说清产品
2. 技术栈       —— 明确或让 AI 定（但要审）
3. 关键功能     —— 列 3-5 个核心点，别贪多
4. 验收标准     —— 怎么算做完了
```

写清这四点，AIcoding 的交付质量会高一个档次。
